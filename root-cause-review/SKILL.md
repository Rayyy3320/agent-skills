# Root Cause Review

仅诊断或评审时保持只读；任务包含修复时，在已授权范围内实施。

1. 从原问题的实际行为、已有失败修复和相关代码出发，确定预期与实际差异。沿触发入口追踪到产生错误的状态、数据或约束，只检查影响诊断的路径。
2. 区分症状、现有补丁和根因。用复现、日志、调用链或可观察状态支持因果判断；有竞争解释时，选择能区分它们的最小检查。无法运行时标明推断与缺失证据。
3. 根据证据，以恢复已确认的数据或行为约束为边界选择最小充分修复，优先删除已被替代的逻辑、合并重复实现，保留必要保护。结构问题修正结构，局部错误局部处理；不增加掩盖错误的兜底、兼容层或无关重构。
4. 复用现有工具验证原问题，并检查能改变同一约束的其他入口，选择能暴露同类漏口的场景。验证失败先区分修复缺陷、既有故障与环境阻碍；无新证据不重复尝试。
5. 只有重复失败的证据和预期长期收益足以抵偿维护成本时，才建议结构、类型、工具或规范上的持久约束；新增工作须属于当前授权范围。

交付根因及依据、修复或建议、实际验证结果和未验证项。没有可靠证据时明确说根因尚未确认，不用新增流程、报告文件或规则代替诊断。

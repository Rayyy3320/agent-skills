# Root Cause Review

仅诊断或评审时保持只读；任务包含修复时，在已授权范围内实施。

1. 从原问题的实际行为、已有失败修复和相关代码出发，确定预期与实际差异。沿触发入口追踪到产生错误的状态、数据或约束，只检查影响诊断的路径。
2. 区分症状、现有补丁和根因。用复现、日志、调用链或可观察状态支持因果判断；有竞争解释时，选择能区分它们的最小检查。无法运行时标明推断与缺失证据。
3. 根据证据选择最小充分修复。结构导致错误时修正结构，局部错误则局部处理；不为追求“治本”扩大成无关重构，也不增加掩盖错误的兜底或兼容逻辑。
4. 检查已有补丁是否仍有独立用途；只删除已证明被根因修复取代的部分，保留必要的边界保护。
5. 复用现有工具验证原问题，并检查与根因直接相关的受影响行为。验证失败时先区分修复缺陷、既有故障和环境阻碍，再决定下一步；没有新证据不重复同一尝试。
6. 只有重复失败的证据和预期长期收益足以抵偿维护成本时，才建议结构、类型、工具或规范上的持久约束；新增工作须属于当前授权范围。

交付根因及依据、修复或建议、实际验证结果和未验证项。没有可靠证据时明确说根因尚未确认，不用新增流程、报告文件或规则代替诊断。

# 项目文档选型指南

**先确定信息缺口，再决定承载方式；不要根据模板列文件清单。** 用于规划文档体系或决定新增、合并、拆分、删除文档；普通代码与单文件修改不需要读取。

## 选择方法

1. **查现状**：看项目目标与阶段、已有文档分工、已确认决策及代码/配置中的现有权威来源；已有合适载体则沿用。
2. **识别具体需求**：是谁在什么任务中需要哪项信息？能否直接从代码、测试、Schema、配置、设计原文件、Git 或现有文档可靠获得？能获得就优先引用，不复制。
3. **判断持久性**：跨任务有价值、难从实现还原、需要交接或影响重要决策的信息，值得保留；一次性探索通常留在对话、Issue、PR 或临时 Plan。
4. **选择最小载体**：优先补充现有文档；只有使用者、职责、更新周期或检索负担明显不同，独立文件更经济时才新增或拆分。
5. **限定维护责任**：写清当前事实、确认目标或未定提案的状态；只在必要时从 README/索引增加入口，不创建空目录或说明性报告。

用户明确要求某份交付文档时，应按要求提供，不以通用选型原则否决；但不自行扩建整套配套文件。

## 根据需求选载体

| 实际信息需求 | 优先去向（不是必建项） |
| --- | --- |
| 项目入口、启动与简要导航 | 现有 `README.md` |
| 长期、项目特有的 Agent 行为约束 | 局部/项目 `AGENTS.md`；若全局已涵盖则不重复 |
| 为谁做、业务目标、已确认需求 | 已有产品说明；必要时 `PRD.md` |
| 某次交付的行为、边界和验收要求 | 当前任务描述；需跨线程交接时 `spec.md` 或功能 Spec |
| 模块、页面、数据、服务的关系 | 已有架构说明；复杂且需长期维护时 `architecture.md` |
| 视觉、交互、设计系统或详细设计 | 已有设计来源；确有必要时 `design.md`（先约定用途） |
| 重大决策的理由及替代项 | 现有决策记录；不能被实现推断时再增加 ADR |
| 长期优先级和阶段目标 | 现有任务管理；需要可共享稳定视图时 `roadmap.md` |
| 复杂任务可中断、可恢复的实施路径 | 临时计划；确有统一 ExecPlan 写法需求时另设 `PLANS.md` |
| 外部接口或数据字段事实 | 代码/Schema/自动生成文档；必要时 API Reference |
| 重复部署、运维、故障恢复 | 现有命令；复杂或关键操作再写 Runbook |
| 对外贡献或版本发布 | 按需要用 CONTRIBUTING / CHANGELOG / SECURITY，不默认全建 |

## 按项目规模与性质调整

- **短期 Demo / 原型**：通常入口和少量不可从实现还原的产品或设计约束即可。已冻结、跨线程执行的设计可以有单独 Spec；不要强制齐备 PRD、Roadmap、ADR 等。
- **个人长期应用**：从已有入口与约束开始，按需求增加 PRD、设计、架构或功能 Spec；不是一套固定组合。
- **多模块 / 多人长期项目**：跨团队边界、重大决策、部署恢复等更可能需要结构化文档和索引；只有文档已产生实际维护成本时才考虑定期检查机制。
- **SDK / 开源库 / CLI**：对外使用说明、API Reference 更有价值；确有协作和发版场景再添加 CONTRIBUTING、CHANGELOG。
- **3D / 嵌入式 / 设计项目**：优先保存不能从 Blender、CAD、固件、原理图等原生资产还原的意图、约束、步骤和验收依据；数据表、BOM、连线图不必强行写进 MD。

## 是否改动现有文档体系

| 操作 | 有价值的触发证据 |
| --- | --- |
| **不动** | 当前信息已可定位、准确，新增只是为了“看起来完整”。 |
| **新增** | 存在明确读者和持续/高价值信息缺口，既有载体不能经济承载。 |
| **合并** | 多文件独立维护相同事实、反复不一致；合并后仍易检索。 |
| **拆分** | 不同受众、更新节奏或职责已造成明显检索/维护摩擦。 |
| **删除/归档** | 内容明确失效、被取代或只是完成的临时状态；保留有效的独有决策和必要依据。 |

若现状与已确认目标冲突，先判断是实现尚未完成还是文档确实过时；不能只因代码不同就擅自重写产品目标。
